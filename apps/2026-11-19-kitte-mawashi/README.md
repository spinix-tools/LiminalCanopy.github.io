# 切手まわし / KITTE MAWASHI

**2026-11-19｜MVP v1.0｜MIT｜外部API・アカウント・課金なし**

## 狙う利用者・選定理由

旧額面切手を使い切りたい個人、ハンドメイド発送者、小さな事務所など。複数の封筒へ同時に切手を貼る際、**一通ごとの最適解を先に選ぶと、後の郵便物に必要な切手が足りなくなる**問題に着目した。

日本郵便は2024年6月13日に、2024年10月1日から定形郵便物を84/94円→110円、通常はがきを63円→85円へ改定すると発表。現在の公式料金表も定形50g以内110円、通常はがき85円と案内している。古い額面が手元に残る利用場面の傍証だが、ユーザー数・支払意思は未調査。

## 国内・海外の競合（2026年11月19日確認）

| 対象 | 確認した機能 | 位置づけ |
|---|---|---|
| 国内向け **StampCal** | 在庫を考慮した複数方針の切手組合せ、15か国対応、写真切手帳 | 単一料金の最適組合せには強い直接競合 |
| 日本語Web **Found Tools Stamp Combination Finder** | 切手在庫を指定して最大5案を提示 | ブラウザベースの近接競合 |
| 海外 **collectpostmarks.com Stamp Optimizer** | 米国の手持ち額面による必要料金の組合せ・料額表 | 旧額面活用の海外需要の存在を示す |
| 2004年の国内「切手組合わせ」 | 手持ち在庫の計算と使用後の残数減算 | 在庫の差引自体は新規ではない |

**差別化仮説：** 複数通に対して手元の在庫を**一度に最適割当**し、貼付枚数の上限と各通の過払許容量を守り、一通ずつ選ぶ場合との違いを可視化する。競合にないことの網羅的証明ではなく、機能構成の仮説。収益性・継続利用率は未検証。

## MVPの機能

- 切手1〜8額面（各0〜30枚）、郵便物1〜4通（各貼付1〜5枚まで）を入力し、**切手の在庫を複数通で共有した割当を厳密探索**。
- `超過額 → 使用枚数` または `使用枚数 → 超過額` の辞書式最小化、各通の超過上限0〜100円、貪欲な順番計算との比較。
- 全額面・枚数を表示し、割当を確定すると在庫を減算。直前の確定だけUndo可。
- 端末内localStorage保存、設定JSON入出力、配分CSV出力（CSV式注入対策）、ブラウザ印刷、スマートフォン対応。
- 誤入力・解なし・探索状態上限（16万）を明示。探索上限時は最適解を**表示しない**。

**デモ**：100円×1、70円×1、30円×1、10円×1を、必要額100円/110円・各最大2枚の2通に振分け。順番計算では100円切手を先に使い後の110円が不可能だが、共同計画なら**70+30=100円、100+10=110円**と割り当て、超過0円で全件成功。

## 検証（この実行）

- `node --test engine.test.cjs` → **13/13合格**。うちランダムな小型問題**150条件**を別実装の全列挙と照合。
- `python browser_test.py` → **Chromium UI検証33/33合格**。計算、編集、在庫確定・Undo、JSON復元、CSVの式注入防止、スマホ幅などを確認。実際のソースをHTMLへインライン展開して検査。`localStorage`は管理環境の制限により模擬。
- `node --check engine.js && node --check app.js` → 合格。
- 直接の`file://`起動、実ブラウザの永続保存、実際の切手貼付面積、郵便料金と切手使用資格、印刷実機は未検証。

## 使い方

同じフォルダの `index.html`、`style.css`、`engine.js`、`app.js` を維持し、`index.html` を通常のブラウザで開く。`npm install`不要。テストはNode.js v22とPython Playwright + Chromiumを使用する。

**重要な限界**：郵便物の料金自体は入力値であり、このアプリは重さ・形・配達オプションから料金を判定しない。利用前に日本郵便公式の最新表で確認すること。貼付できる面積・切手の有効性・扱いも対象外。探索は規定内なら全候補を調べるが、上限を超えた場合は安全に停止する。個人情報の収集やネット送信を行う機能はない。自由入力欄へ宛名を記載する必要もない。
