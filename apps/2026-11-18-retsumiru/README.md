# れつみる / RETSUMIRU — 受付行列・スタッフ配置シミュレーター

小規模イベントの**開催前**に「30分間の来場予想・対応時間・スタッフ配置」を入れ、先着順受付の行列と終了時の未完了人数を試算する**登録不要のWeb MVP**。来場者の電話番号・名前などの個人情報を収集しない。

## 誰に / なぜ選んだか（2026-11-18調査）

- **ターゲット**: 地域マルシェ・学校祭・小規模展示会・ポップアップの受付責任者。前回までの備品予約、木材加工、焼成、折本、字幕、編み物、配色、釣銭、紙箱、音響転換とは異なる「待ち行列の予測・シフト配分」領域。
- **日本**: 電通『情報メディア白書2026』によると、2024年の国内イベント産業規模は2兆8,535億円（2019年比109.2%）。イベント市場は広義の指標で、本ツールの直接的購買意思を表さない。[電通](https://www.dentsu.co.jp/knowledge/infomedia/2026/index8.html)。国内の[Airウェイト](https://airregi.jp/wait/function/)は番号券・呼び出し・業務分析を提供。 [VACAN](https://corp.vacan.com/)も混雑の可視化・予測を提供。
- **海外**: [Waitwhile](https://waitwhile.com/solutions/queue-management-system/)と[QLess](https://www.qless.com/products/)は遠隔順番待ち・受付運用を扱い、[Qmatic Queue Simulation](https://www.qmatic.com/q-store/queue-simulation)はスタッフ数に基づく行列予測も提供。従って「行列をシミュレーションする」自体は新規機能ではない。米Grand View Researchは2026年の世界行列管理システム市場を推計9億4,460万ドルと掲載しているが、推計方法や価格帯には不確実性がある。[原典](https://www.grandviewresearch.com/industry-analysis/queue-management-system-market-report)。

## 差別化仮説

**実運用の電子受付を導入せず、イベントの前夜に30分単位の人数・スタッフ配置をオフラインで比較し、どの30分枠に1人追加するかを同じ乱数条件で公平に試せること。** 既存の包括的な順番待ちSaaSではなく、導入手順・来場者情報・月額契約を不要とする「事前の人員配置検討」に絞る。ユーザーインタビューや有料化可能性は未検証。

## 使い方

`index.html` をChrome/Edge/Firefoxなどのブラウザで開く。外部JS/CSS/通信/ビルド不要。まずサンプル条件で計算 → 来場者・スタッフ数・対応時間を変える → 再計算 → 「30分だけ1名追加」の推奨案を適用。設定は端末内の `localStorage` に保存。JSON設定を持ち出して別端末へ移せる。

## 実装済み機能

- 開始時刻・イベント名・30分枠2〜12個・到着予想0〜150人/枠・受付人数1〜10人/枠の編集
- 1人の対応時間（分）、待機列の上限、許容待ち時間、乱数シード、20/80/160回試行
- 再現可能な来場・処理時間の乱数生成、**1分単位**のFIFO受付シミュレーション。平均待機、90パーセンタイル、最大列、対応完了・未対応・入列不可・許容待ち時間超過を表示
- **同一乱数列**で30分間だけ窓口を1名増員した全候補を評価し、スコア改善順に提示。ワンクリック適用
- SVGの待機人数推移、CSV結果、JSON設定出入力、印刷、レスポンシブUI、端末内保存

## 計算上の仮定 / 読み方

- 各30分枠に指定人数が一様にランダム到着。処理時間は平均指定値の65〜135%で独立に分布させ、整数分に丸める。全試行で枠の総到着人数は固定。実際の集中到着・グループの分布は再現していない。
- 先着順・単一列。時刻境界の在席スタッフ数が切り替わり、前の枠から継続中の対応は完了まで続く。新規対応は当該枠のスタッフ数の上限で開始する。**閉場時に受付中または待機中**の人は未完了に分類し、延長運営は計算しない。
- 平均待機・90%点・待機しきい値超過率は**閉場までに完了した人のみ**に対する統計。未完了者の待機は入っていない。入列不可は列の上限に達し拒否された人数。高負荷時には完了者だけの統計が良く見えるバイアスがあるので、必ず未完了・入列不可を併記する。
- 改善スコア = 1試行あたりの完了者の待ち時間総和 + 未完了数×許容待ち時間×4 + 入列不可数×許容待ち時間×6。単位は**比較用ポイント**で、貨幣・健康・安全に関する尺度ではない。推奨案はスコアの改善幅を大きくするだけで最適解や因果効果を保証しない。
- 待機上限は便宜的な人数の上限で、消防や避難の安全基準には一切対応しない。現場の動線・休憩・優先対応・急な欠勤等は扱わない。

- `node --test engine.test.cjs`: **15/15 合格**。バリデーション・乱数再現・保存則（到着 = 完了 + 未完了 + 入列不可）・列の上限・窓口増員・候補比較・境界時刻など。
- `python browser_test.py`: **30/30 Chromium操作試験合格**。フォーム編集/増減・結果描画・おすすめ案適用・JSON/CSVダウンロード/復元・端末状態復元・印刷呼び出し・モバイルレイアウトを確認。管理環境ではlocalhost HTTPアクセスがブロックされるため、**HTML/CSS/JS実ソースをブラウザ文書へ直接注入し、localStorageを模擬**。そのため本番配信時のHTTP読み込みと実ブラウザでのストレージ持続性は別途要検証。印刷紙面・他ブラウザの互換性も未確認。
